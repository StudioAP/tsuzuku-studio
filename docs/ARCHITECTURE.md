# 技術設計

## 構成を小さく保つ

HTML、CSS、ブラウザのJavaScript ES Modulesを使う静的アプリです。実行用・ビルド用npm依存は0。Nodeは開発サーバー、ファイルコピーのビルド、テストに使い、本番にNodeサーバーは置きません。

この規模ではReact/Next.js、認証基盤、データベースサーバー、画像アップロードAPIを導入する理由が薄く、設定や保守の増加を避けました。必要な追加機能が具体化するまでは、フレームワーク置換ではなく既存の小さなモジュールを保守します。

```text
iPhoneの写真選択
  → ファイル形式確認
  → ブラウザ内デコード・作業用JPEG化
  → 写真ごとの非破壊な回転・トリミング
  → project + assets（メモリ）
      ├→ IndexedDB（このブラウザの下書き）
      ├→ buildScene（横長の仮想座標）
      │   ├→ drawPage（低解像度プレビュー）
      │   └→ drawPage × ページ数（1080px出力）
      └→ 任意の .tsuzuku ファイル
  → 生成済みJPEG/PNGの一覧
  → ユーザー操作でOS共有 / 個別保存 / ZIP
  → ユーザーがInstagramで投稿

配信サーバー → HTML / JS / CSS / アイコンのみ
写真 → 配信サーバーという経路は実装しない
```

## モジュール

| ファイル | 責務 |
|---|---|
| `model.js` | 型に相当する構造、定数、自動分割、一段／指定位置の並べ替え、結合・分離、入力検証 |
| `layout.js` | 写真の表示矩形と全ページ共通の仮想シーン。純粋関数。 |
| `images.js` | マジックバイト判別、画像読み込み、作業用JPEG化、サムネイル、2画像キャッシュ |
| `renderer.js` | 仮想シーンを1ページずつ描画。キャンセル、進捗、JPEG/PNG化 |
| `sharing.js` | 共有可否確認、クリック直後の共有、ダウンロード、出力ZIP |
| `storage.js` | IndexedDBのprojects/assetsストア。保存を1トランザクションにまとめる。 |
| `backup.js` | 下書きのエクスポートとバリデーション付き復元 |
| `zip.js` | 依存なしのZIP STORE方式。CRC、ディレクトリ、サイズ、パス確認 |
| `app.js` | Studio UIと状態変更、画面位置を保つ選択写真操作、undo/redo、保存の直列化、ダイアログ、エラー表示 |
| `demo.js` | ネット取得しないデモイラスト |
| `sw.js` | アプリ本体だけのキャッシュ。写真データは扱わない。 |

## データ構造

```js
project = {
  version: 1,
  id: 'uuid',
  title: '新しいカルーセル', // v1では内部値。タイトル編集UIは設けない。
  ratio: '4:5',
  theme: 'edge',
  format: 'jpeg',
  blocks: [{
    id: 'uuid',
    photoIds: ['asset-id'], // 単独は1、組み合わせは2
    span: 2,                // 出力ページ1〜6枚
    layout: 'single',       // single | duo | overlap
    fit: 'contain',         // contain | cover
    transforms: {
      'asset-id': { zoom: 1, focusX: 0, focusY: 0 }
    }
  }]
};
asset = {
  id: 'uuid', name: 'photo.jpg',
  width: 3000, height: 2000, // 作業用JPEGの向き補正後サイズ
  originalWidth: 6000, originalHeight: 4000,
  blob: Blob, thumbnail: Blob,
  preprocess: {
    rotation: 0, // -180〜180度
    zoom: 1, focusX: 0, focusY: 0, // 1〜3倍、白場を出さない可動範囲内の-1〜1
    crop: { left: 0, right: 0, top: 0, bottom: 0 } // 元写真と同じ固定フレームの各辺を0〜0.95で非破壊指定
  }
};
```

写真は各プロジェクト内で1回参照する。組を分ける場合は出力上限を確認する。assetsには未参照写真を残さない。取り込み拒否のファイルや削除済みデータを黙って復帰させない。

前処理は元の作業用JPEGを再エンコードして上書きせず、回転角、追加倍率、可動範囲内の位置、元写真と同じ固定フレームに対する四辺の切り取り率をassetへ保存する。回転時は固定フレームの四隅を写真が覆う最小倍率を `max(|cosθ| + H/W×|sinθ|, |cosθ| + W/H×|sinθ|)` で求める。さらに各出力枠の四隅を画像ローカル座標へ逆変換し、全点が元画像内に残る平行移動範囲を算出する。ドラッグ位置はその範囲に制限するため、回転・拡大・移動を組み合わせても白場を残さない。レイアウト計算は固定フレームから手動トリミングを差し引いた有効サイズを使い、描画時だけ自動拡大・追加拡大・位置・回転・切り取りを適用する。中央正方形プリセットは固定フレーム中央の最大正方形を選ぶ。4:5投稿で正方形を`contain`・1ページにすると1080×1080で中央配置され、上下各135pxが背景になる。前後の2ページ連結ブロックとは独立して並べられる。

undo/redoはメモリ内に各20段階程度の履歴を保持する。Blobは参照を共有し、画像を毎回複製しない。履歴は再読み込み後には残らない。ローカル保存はその時点のプロジェクトのみで、履歴を永続化しない。

## つながる分割の計算

出力1枚を `W=1080`, `H=1350`、対象写真の分割数を `n=2` とすれば、対象写真の表示枠は横2160px相当です。前の写真の出力枚数も足した、全ページ共通のX座標で配置します。

写真の拡大率は、全体表示なら `min(frameW / imageW, frameH / imageH)`、枠いっぱいなら `max(...)`。その結果にユーザーのzoomを掛け、focusX/Yで位置を決めます。座標の整数化は共通シーンで一度だけ行います。

各出力ページでは同じシーンに対して `translate(-pageIndex * W, 0)` して描画します。左ページと右ページで別々のcover計算をしません。余白は写真の組全体の外側につけ、内部ページ境界にはつけません。

プレビューは同じシーンを幅320pxで描画します。UIに載せる番号と破線はCanvasの外側のDOM要素なので、出力に混ざりません。

「2枚を並べる」は1ページなら上下、2ページ以上なら左右。「重ねてつなぐ」は大きな写真に小さな写真を重ねる定型レイアウトで、自由なドラッグ編集ではありません。

## 画像とメモリ

作業用の長辺4096px・8MP上限は、画質とiPhoneメモリのトレードオフです。48MPの元写真を20枚すべてフル解像度で保持しません。JPEG化と縮小は取り込み時に1度行い、そのBlobと320pxサムネイルを保持します。元写真の撮影情報はCanvasの再エンコードには引き継ぎません。

本番の出力Canvasは1枚ぶんだけで、ページごとに再利用します。描画に必要な画像のデコードキャッシュは最大2枚。終了・キャンセル時に画像とCanvasを解放します。生成済みの出力Files自体は保存操作のためにメモリに残します。

全ページぶんを繋げたCanvasは、比較基準を作るブラウザテストでだけ使います。製品コードへ移さないでください。

## 保存と共有

450msの変更待ちとPromiseチェーンで保存を直列化し、古い保存結果で「保存済み」表示を上書きしないようrevisionを比較します。IndexedDBでは新しい写真Blobだけを`assets`へ追加し、軽量な前処理値は`assetEdits`へ分離して更新します。現在は1アクティブプロジェクト、同時編集1タブです。DB version 1の既存下書きはversion 2へ自動更新し、前処理なしとして読み込みます。

共有は**生成フェーズと共有フェーズを分離**します。生成後にファイル一覧を表示し、ユーザーの次のクリックの同じ呼び出し経路で `navigator.share({files})` を実行します。先に重い処理やawaitを入れると、共有に必要なユーザー操作状態が失われるためです。[S3]

`canShare({files})`、安全なコンテキスト、APIの存在を毎回確認します。テキストやURLを共有データに混ぜず、画像ファイルだけを渡します。共有成功は写真への保存保証ではないので、「写真アプリで保存結果を確認」と表示します。

下書き持ち出しは、非圧縮ZIPの `.tsuzuku` ファイルです。project.jsonと作業用JPEGを入れます。写真を含むので秘密情報に準じて扱い、Gitから除外します。任意のファイル保存であって、アプリの自動同期ではありません。

## キャッシュと配信

`build.mjs` が配信対象のファイル内容をハッシュ化し、`sw.js` のキャッシュ版に埋め込みます。キャッシュの名前には配信パスも含め、同一オリジン上の別パスのキャッシュを不用意に削除しないようにしています。パスはすべて相対指定で、GitHub Pagesのリポジトリ配下でも動く構成です。

初回はオンラインが必要です。ナビゲーションは通信を試し、失敗したらキャッシュから開きます。列挙済みのアプリ資産だけをキャッシュし、Blob URL、ユーザー写真、下書きはService Workerに渡しません。

開発時のlocalhostでは通常Service Workerを登録しません。`?sw` で明示的に有効化できます。更新直後に古い画面が残る場合は、一度下書きをファイル保存してからタブを閉じて開き直します。キャッシュやサイトデータを消す前に下書きを保護してください。

## セキュリティ境界と既知の制約

ユーザー由来文字列はHTMLエスケープし、CSPでスクリプトを同一配信元に制限します。CSPは防御の補助であって、将来追加した同一オリジンの不適切なコードから自動的に守るものではありません。レビュー時は通信追加を必ず確認してください。

IndexedDBはブラウザのオリジンに属します。GitHub Pagesの同じホスト配下には、信頼できるアプリだけを置いてください。パスだけでは強い保存領域の分離になりません。複数の本アプリを同じオリジンに置く場合、現状は同じDB名を共有するため、別オリジンかDB名分離を検討してください。

画面とロジックは分離していますが、`app.js` は意図的に小規模な一枚のUI制御クラスです。機能が増えて複雑になったときだけ段階的に分割します。通知の文言、手順、実機確認を優先し、先に認証やクラウド基盤を導入しないでください。
